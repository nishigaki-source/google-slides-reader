# Phase 0 技術検証

前提：読み上げ対象は本文とスピーカーノートの両方。利用者は自分のみ。音声は標準音声（`chrome.tts`）を使う。

## 1. 検証済み（Claude の組み込みブラウザで、Google 公式の公開サンプル資料を使って確認）

### テキストの取得方法

| 方式 | 結果 | 判断 |
|---|---|---|
| 画面の SVG から読む | 編集画面では `#pages svg g[id^="editor-<slideId>"]`、ノートは `#speakernotes-workspace svg` にある。ただし文字は単語や行ごとに別々の `<text>` に分かれていて、**単語の間の空白が失われている**（例：`{Name` と `Here}` が別要素）。ノート欄は表示幅に合わせて 1〜2 文字ずつ折り返されていた | 読み上げ用の文字取得には使わない |
| `export/txt` | 取得できる（ページから相対 URL で fetch すれば Cookie 付きで送られ、`googleusercontent.com` へのリダイレクトも CORS `*` で通る）。本文とノートは含まれるが、**どこからがノートか、どこでスライドが切り替わるかの区切りがない** | 使わない |
| **`export/pptx`** | **採用**。`ppt/slides/slideN.xml` に本文、`ppt/notesSlides/notesSlideN.xml` にノートがスライドごとに分かれて入っている。ノートの図形名が `Google Shape;33;<スライドのオブジェクトID>:notes` となっているため、**画面の URL にある `slide=id.<ID>` と対応付けられる** | 採用 |

- pptx の取得と解析：3MB（画像入り・5 枚）の取得に約 1.5 秒。解凍は `DecompressionStream('deflate-raw')` で動き、外部ライブラリは不要だった。
- **ページには Trusted Types が有効で、`DOMParser` が使えない**（`This document requires 'TrustedHTML' assignment`）。そのため XML は正規表現で必要な要素だけを拾う実装にした（`src/lib/pptx.js`）。Node 上で、サンプルの pptx から全 5 枚の本文・ノート・ID を正しく取り出せることを確認済み。

### 表示中のスライドの判別とページ送り

| 画面 | 表示中のスライドの取得 | ページ送り |
|---|---|---|
| 編集画面 | URL の `#slide=id.<ID>`（`?slide=` は開いた時点の値なので、`#` を優先する）。URL に無い場合は `#pages` 内で面積が最大の `g#editor-<ID>` を使う（以前に表示したスライドも非表示のまま残るため、先頭の要素では判定できない） | `ArrowRight` の KeyboardEvent で進んだ ✅（実際の資料で確認） |
| `/present` を直接開いた場合 | URL の `?slide=id.<ID>`、または `.punch-viewer-svgpage-svgcontainer svg g[id]` | `ArrowRight` の KeyboardEvent を発生させると進んだ ✅ |
| 編集画面から開いたスライドショー | 同一オリジンの `iframe.punch-present-iframe` の中にある、上と同じ要素 | iframe 内の文書に `ArrowRight` を発生させると進んだ ✅。`Escape` で終了する |

→ スライドショーの iframe は同一オリジンなので、トップフレームの content script から中身を読める。`all_frames` は不要。

### 読み上げ順

pptx 内の図形は重ね順（作成・前面移動の順）で並ぶため、見出しが最後に読まれるスライドがあった（実際の資料で発生）。
タイトルのプレースホルダーを先頭にし、残りは位置の順（上→下。y の差が約 0.33 インチ未満なら同じ行とみなして左→右）に並べ替える。
スライド上で位置が省略されたプレースホルダーは、レイアウト→マスターの順に同じ idx・type の位置を探して補う。

- 既知の制約：左右 2 段組で、左右の段の上端がそろっていると、「左上→右上→左下→右下」の順に読む（段ごとには読まない）。グループ内の図形の座標は、グループの座標系のまま比べている。

## 2. ご自身の Chrome で確認が必要な項目

組み込みブラウザには Google アカウントでログインしていないため、次の項目は検証用拡張で確認してください。

1. **非公開（自分の）資料**を pptx で取得できるか（ログイン中の Cookie が使われるか）
2. `chrome.tts` で使える**日本語の音声**と、そのイベント（`end`、`word`）が届くか
3. **日本語の本文とノート**が正しく取り出せるか
4. 自分の資料で、表示中のスライドとの対応付け・ページ送りが正しく動くか

### 検証用拡張の読み込み手順

1. Chrome で `chrome://extensions` を開く
2. 右上の「デベロッパー モード」をオンにする
3. 「パッケージ化されていない拡張機能を読み込む」を押し、このフォルダ（`スライド音声読み上げ`）を選ぶ
4. 日本語の本文とノートがある自分の Google スライドを開く（すでに開いている場合は再読み込み）
5. ツールバーの拡張アイコンを押すと右側にサイドパネルが開くので、次の順に操作する
   - 「2. 使える音声」で「こんにちは…」を読ませる
   - 「3. 取得する」
   - 「4. 現在のスライドを読む」
   - 「5. 次へ →」を試す：編集画面と、URL の末尾を `/present` に変えた画面の両方で
     （全画面のスライドショーではツールバーが隠れるため、`/present` の URL を通常のタブで開いて試す）
6. 「6. 検証結果をコピー」を押し、貼り付けて共有する（本文やノートそのものは含まれず、件数・音声名・イベントだけが入る）

### 実際の資料での結果（2026-09-23、Chrome 153 / macOS）

| 項目 | 結果 |
|---|---|
| 非公開資料の pptx 取得 | ✅ ログイン中の Cookie で取得できた。ただし **12 枚で 37〜61 秒**かかり、時間も毎回大きく変わる（サンプルは 5 枚で 1.5 秒） |
| 日本語の本文 | ✅ 取得できた。読み上げ順の問題（見出しが最後）は位置順の並べ替えで対応済み |
| スライドの対応付け | ✅ ID で一致した。この資料の ID は `p1`〜`p12` という形式 |
| 日本語の音声 | ✅ 10 件。Kyoko と Eddy などの端末内の音声は `word` イベントに対応。`Google 日本語` はオンラインの音声で、`word` イベントは届かない |
| 読み上げ | ✅ Kyoko で `start→end`、`word` イベントが 67 回届いた |
| ノート | ✅ ノートを書いたスライド（1 枚）のノートを取得できた |
| ページ送り | ✅ 編集画面で `ArrowRight` を送ると `p7→p8` に進み、ID と何枚目かの両方が追従した。自分の資料の `/present` では未確認（公開サンプルでは確認済み） |

## 3. 次の段階（Phase 1）への設計判断（仮）

- テキストの取得：**content script が pptx をエクスポートして解析する**。Slides API と OAuth は使わない（自分用なので、この方式で十分と判断）。
- 再取得のタイミング：再生開始時に 1 回だけ取得し、ボタンで手動更新できるようにする。編集した内容をすぐ反映させる仕組みは後で検討する。
- **最大の課題は取得時間（37〜61 秒）**。次の 3 つで対応する。
  1. 取得結果を `chrome.storage.local` に保存し、同じ資料なら再利用する（手動で更新するボタンを付ける）
  2. 資料を開いた時点で、裏で取得を始める
  3. 取得が終わるまでは、画面に表示されている文字（SVG の `<text>`）で表示中のスライドを先に読む
- 音声：標準は端末内の音声（Kyoko など）にする。`word` イベントが届くので、読んでいる箇所の強調表示にも使える。
